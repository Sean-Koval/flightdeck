# Getting started

Requires [uv](https://docs.astral.sh/uv/) (it brings Python 3.12) and git.

## The boundary

Flightdeck is the **Judge** in Run / Judge / Govern ([ADR-0001](decisions/0001-boundary-with-hangar.md)):

- Flightdeck has **no sandbox code** and holds no sandbox, provider or team credentials.
- It reads hangar's three versioned interfaces, `hangar.manifest/v1`, `hangar.trace/v1` and `hangar.experiment/v1`
  ([hangar spec 0014](https://github.com/Sean-Koval/hangar/blob/main/docs/specs/0014-sister-tool-interfaces.md),
  [hangar `docs/api/`](https://github.com/Sean-Koval/hangar/tree/main/docs/api)), from a GCS → Parquet data plane or
  hangar's REST API. [Contracts](contracts.md) lists everything it reads and writes.
- It owns **sampling** (how many trials, which tasks, when to stop) and asks hangar to execute trials; hangar executes
  `task × variant × n` against pinned conditions and does no analysis.
- The only runner here is the local Docker runner ([#18](https://github.com/Sean-Koval/flightdeck/issues/18), `--backend local`), for fixtures and CI
  ([Running experiments](runners.md#local)).

## End to end on the fixture experiment

The synthetic fixture experiment has 12 tasks × 2 variants × 3 trials, with an infrastructure failure hangar retried,
a cancelled, a drifted and a still-running trial, a truncated trace and an invalid task; no team data. Its
`decision.yaml` is committed (in a git repository inside the export directory) before the first trial, so the report
gives a verdict.

```sh
uv run python scripts/fixture_export.py demo/export          # what `hangar experiment export <id> -o DIR` writes
uv run flightdeck ingest export demo/export --out demo/plane
uv run flightdeck check run --data demo/plane --date 2025-10-16 --specs specs/examples/team-default.yaml
uv run flightdeck stats compare job-expdemo --data demo/plane                   # resolved, paired by task
uv run flightdeck stats compare job-expdemo --data demo/plane --metric cost_usd
uv run flightdeck report experiment job-expdemo --data demo/plane \
    --decision demo/export/decision.yaml --out demo/report.md
GITHUB_TOKEN=... uv run flightdeck report post demo/report.md --to owner/repo#123   # one comment, updated in place
```

`demo/` is ignored by git. The front page's recording and screenshots are this session, generated by
`docs/assets/build.py` ([Contributing](https://github.com/Sean-Koval/flightdeck/blob/main/CONTRIBUTING.md)).

`check run` prints one line per spec with its counts over the day's units, and `stats compare` ends with the power
line and the exclusions:

```text
spec	never-push-main	pass=72 fail=0 not_applicable=0 unknown=1
spec	tests-before-commit	pass=1 fail=0 not_applicable=71 unknown=1
...
Paired difference treat - control: **+21.2 pp**, 95% CI +1.5 pp to +43.9 pp (task bootstrap; 11 tasks, 63 trials; 3 concordant, 8 discordant tasks).
At 11 paired tasks x 3 trials the minimum detectable lift at 80% power is about 35% (simulated).
Excluded: cancelled 1, drift 1, infra_error 1, not finished 1, task_invalid 6.
```

The fixture is built with a large effect (treat about 20 points better), and even so the interval at 11 paired tasks
runs from +1.5 to +43.9 points. A real harness change usually moves less: see
[what flightdeck can tell you](statistics.md#what-flightdeck-can-tell-you).

## Against a real hangar

`HANGAR_TOKEN=... flightdeck ingest experiment <id> --hangar https://<your hangar>` (or `ingest job` /
`ingest session`), then the same `check run`, `stats compare` and `report` with the default data directory
(`~/.flightdeck/data`, or `FLIGHTDECK_DATA_URI`). Keep that directory private
([ADR-0002](decisions/0002-public-code-private-data.md)). To plan and submit trials, see
[Running experiments](runners.md); every command and flag is in the [CLI reference](cli.md).

A worked setup to start from: agent-factory's
[`examples/team-harness/flightdeck`](https://github.com/Sean-Koval/agent-factory/tree/main/examples/team-harness/flightdeck) has a suite (stable against candidate, the
ai-dlc workflow plugin off and on), a pre-registered `decision.yaml` and behavior specs. It ships no tasks, so
`flightdeck experiment run flightdeck/suite.yaml --dry-run` stops at `no task under tasks` until you add one
(`flightdeck task new flightdeck/tasks/<id>`, then set `[flightdeck] environment` in its `task.toml`, or `environment`
in the suite).

## Status and code map

v0, pre-release. The analysis code stays within a counted line budget: 3,785 non-blank, non-comment lines under
`src/flightdeck/` (`scripts/loc_budget.py`, enforced in CI; code ported from ai-dlc and hangar is reported but not
counted). It started at 1,500 and was raised by ADRs [0003](decisions/0003-line-budget.md),
[0004](decisions/0004-local-runner-budget.md) and [0005](decisions/0005-post-v0-budget.md); it is full, and any
increase needs a new ADR. Flightdeck has to change one real team decision ([#20](https://github.com/Sean-Koval/flightdeck/issues/20)) before anything else, a UI
included, gets built.

| Module | What |
| --- | --- |
| `flightdeck.dataplane` | `flightdeck.parquet/v1` tables (runs, spans, events, manifests, grades, test_cases), flatteners from hangar's manifest, OTLP trace and experiment index, DuckDB views; `flightdeck query`. See [Data plane](data-plane.md) |
| `flightdeck.dataplane.ingest` | `flightdeck ingest export\|experiment\|job\|session`: hangar REST or `hangar experiment export` into local Parquet, idempotent, validated against vendored hangar schemas. See [Data plane](data-plane.md#ingest) |
| `flightdeck.stats` | Wilson, pass@k, pass^k, clean-run bound, paired task bootstrap, $ per resolved task, McNemar counts, a power simulation (`simulate_power`); `flightdeck stats compare` with exclusions and saturated tasks. See [Statistics](statistics.md) |
| `flightdeck.report` | `flightdeck report experiment`: the markdown report with a pre-registered verdict, posted as one PR or issue comment. See [Reports](reports.md) |
| `flightdeck.specs` | `flightdeck.spec/v1` behavior specs: YAML predicates over `hangar.trace/v1`, a Python reference evaluator and a DuckDB compiler, the trusted-test rule; `flightdeck spec lint\|test`; the nightly runner over the data plane with ADR `checks:`, change-point alerts and `flightdeck check run\|diff`. Mutation scoring of suites: `flightdeck mutate plan\|run\|score`. See [Behavior specs](behavior-specs.md) |
| `flightdeck.tasks` | Harbor-compatible task directories: load, check and digest them, map them onto a `hangar.experiment/v1` spec; `flightdeck task new\|check\|digest`; `flightdeck task import-aidlc` for ai-dlc evaluation suites; sealed holdout custody, `flightdeck holdout brief\|seal\|score\|canary-scan` ([Holdouts](holdouts.md)); the knowledge gold set, `flightdeck knowledge seal\|score` ([Knowledge evals](knowledge-evals.md)); rubric judges, `flightdeck judge label\|calibrate\|score\|estimate` ([Judges](judges.md)); the semver smoke task in `tasks/smoke/`. See [Tasks](tasks.md) |
| `flightdeck.runners` | The experiment submission client: suite plans to `hangar.experiment/v1` specs, a cost gate, `flightdeck experiment run\|status\|collect`. See [Running experiments](runners.md) |
| `flightdeck.ported` | Code moved in and kept close to its source, outside the line budget: hangar's model-concreteness rule and trace classifier; ai-dlc's local runner, evaluation contracts and suite checks |
